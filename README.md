# Приёмник событий с очередью обработки

Тестовое задание: небольшой сервис на Flask + SQLite. Принимает webhook-события по HTTP,
сохраняет их в базу и обрабатывает через собственную очередь на таблице — без брокеров и готовых
движков очередей.

# Инструкция по запуску проекта

**Клонируйте репозиторий**

`git clone https://github.com/nukce1/event-queue && cd event-queue/`

**Установите зависимости**

Poetry:

`poetry install --no-root`

либо обычный pip (Python 3.11+):

`pip install flask pydantic pydantic-settings sqlalchemy pytest`

**Запустите сервис**

```
cd app
python -m flask --app app run --port 5000
```

База данных (`events.db` относительно рабочей папки `app/`) и таблицы создаются автоматически
при первом запуске. Файл `.env` не обязателен — значения по умолчанию подходят для локального
запуска; при желании скопируйте `.env.example` в `app/.env` (путь `.env` разрешается относительно
рабочей папки) и поправьте параметры.

Доступные переменные окружения: `DATABASE_PATH`, `WORKER_ENABLED`, `WORKER_POLL_INTERVAL`,
`RETRY_BASE_DELAY`, `RETRY_BACKOFF_FACTOR`, `LOG_LEVEL`, `LOG_PATH` и другие (см. `.env.example`).

# Проверка работоспособности

**Принять событие**

```
curl -X POST http://127.0.0.1:5000/webhook \
  -H "Content-Type: application/json" \
  -d '{"event_id": "abc-123", "type": "payment_succeeded", "payload": {"amount": 100}}'
```

Ответ: `{"result":"accepted"}`. Повторный запрос с тем же `event_id` — `{"result":"duplicate"}`
с кодом 200, второй записи не создаётся.

**Некорректное тело**

Запрос без `event_id`, с пустым `type`, с `payload` не-объектом или не-JSON телом — ответ 400
с описанием ошибки в поле `detail`.

**Имитация падения обработчика**

```
curl -X POST http://127.0.0.1:5000/webhook \
  -H "Content-Type: application/json" \
  -d '{"event_id": "fail-1", "type": "payment_succeeded", "payload": {"simulate_failure": true}}'
```

Такая задача сделает 3 попытки с нарастающими паузами (по умолчанию 1с и 2с) и перейдёт
в статус `failed`.

**Статистика**

`curl http://127.0.0.1:5000/stats`

```json
{
  "events_by_type": {"payment_succeeded": 2, "refund_issued": 1},
  "tasks_by_status": {"pending": 0, "success": 1, "failed": 1, "skipped": 1}
}
```

# Как прогнать тесты

Из корня репозитория: `poetry run pytest` (или `python -m pytest` при установке через pip).
Тесты используют изолированную временную базу и не трогают `events.db`; фоновый воркер в них
выключен, очередь обрабатывается детерминированно.

# Техническое задание

## Приёмник событий с очередью обработки

Сервис на Flask с базой SQLite.

1. `POST /webhook` принимает JSON вида `{"event_id": "abc-123", "type": "payment_succeeded", "payload": {...}}`
   - `event_id` уникален. Повторный запрос с тем же `event_id` не создаёт вторую запись и отвечает 200.
   - Событие сохраняется в таблицу и ставится в очередь на обработку.
   - Некорректное тело — понятная ошибка и код 4xx.

2. Очередь обработки
   - Отдельная таблица задач со статусами: `pending`, `success`, `failed`, `skipped`.
   - Обработчик берёт задачи из очереди. Обработка — заглушка: функция, которая по типу события
     что-то делает и иногда падает (сымитировано).
   - При ошибке до 3 попыток с нарастающей паузой. После третьей задача переходит в `failed`
     и больше не берётся.
   - Задача не должна остаться в `pending` навсегда ни при каком сценарии.

3. `GET /stats` возвращает счётчики событий по типам и задач по статусам.

Чего не нужно: авторизации, фронтенда, Docker, миграций, деплоя. Библиотеки любые, кроме
готового движка очередей (Celery, RQ, Huey): очередь своя, на таблице.

Стек: Python 3.11+, Flask, SQLite, pytest.

# Принятые решения и почему

- **Слоистая архитектура**: `api` (тонкие HTTP-хендлеры) → `services` (бизнес-логика и доменные
  исключения) → `repository` (вся работа с хранилищем), между слоями — `Protocol`-интерфейсы
  (`protocols/`), сборка зависимостей в `dependencies/`, модели и схемы — в `domain/`.
  Слои заменяются независимо: например, `SqliteStorage` можно поменять на другую реализацию
  `Storage`, не трогая сервисы и хендлеры.
- **Идемпотентный webhook.** Дедупликация опирается на `UNIQUE(event_id)` и
  `INSERT ... ON CONFLICT DO NOTHING` — одна атомарная операция вместо «прочитал-проверил-вставил»,
  поэтому гонка двух одинаковых параллельных запросов не создаст дубль. Ранний выход по
  `rowcount == 0`, повтор отвечает 200 `{"result": "duplicate"}`.
- **Попытка сжигается при взятии задачи, а не при записи результата.** `claim_next_due_task`
  атомарно выбирает due-задачу и сразу увеличивает `attempts`. Даже если процесс упадёт посреди
  обработки, задача не зависнет в `pending` навсегда: после трёх взятий без успеха она перейдёт
  в `failed`. Это и есть гарантия из ТЗ «не должна остаться в pending ни при каком сценарии».
- **Нарастающая пауза**: `RETRY_BASE_DELAY * RETRY_BACKOFF_FACTOR^(номер_попытки - 1)`,
  по умолчанию паузы 1с и 2с. Значения вынесены в настройки, меняются без правки кода.
- **`skipped`** — статус для событий, к которым нет обработчика: обработчики лежат в реестре
  `worker/handlers.py`, добавить новый тип — одна строка-словарь.
- **Имитация падений детерминированная** — флаг `simulate_failure` в payload вместо рандома:
  поведение воспроизводимо и покрыто тестами (в логе smoke-запуска видно 3 попытки с паузами 1с/2с).
- **Один воркер-поток** в процессе Flask (daemon). Для тестового объёма достаточно; claim уже
  атомарен, поэтому масштабирование — это просто ещё один процесс с циклом `process_next_task`
  поверх той же таблицы.
- **SQLite-настройки**: WAL-журнал, `busy_timeout=30` и `foreign_keys=ON` на каждом соединении
  (`database.py`), чтобы фоновая запись воркера не блокировала HTTP-запросы и наоборот.
- **pydantic** — для валидации тела webhook (понятные 400 со списком полей) и для `Settings`
  из переменных окружения / `.env`.
- **Форматирование и линтеры** — black + isort + ruff (line-length 120), конфигурация в
  `pyproject.toml`, pre-commit крючки прилагаются.

# Что сознательно не сделано

- Docker, миграции, авторизация, фронтенд, деплой — прямо исключены ТЗ.
- Graceful shutdown воркера по сигналу остановки Flask: поток daemon и завершается вместе
  с процессом; необработанные задачи остаются в `pending` и корректно подхватываются при
  следующем запуске (метод `stop()` у воркера есть, сигналы не навешаны — для тестового
  объёма посчитал это лишним).
- Конкурентность внутри приложения ограничена одним воркером; несколько воркеров поверх той же
  таблицы потребуют `SELECT ... FOR UPDATE`-подобного захвата строк — в SQLite это
  `BEGIN IMMEDIATE`, при необходимости добавляется в `claim_next_due_task` без изменения
  остальных слоёв.
